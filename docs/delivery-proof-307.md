# Delivery photo evidence — 307

Implemented optional delivery-photo capture, private upload, durable order attachment and authenticated image viewing. The driver card loads previously attached photos and shows “saved with order” only after an order/ID/content-hash-matching server receipt. Failed or lost replies retain the same request ID/image for retry; already attached images are returned idempotently. Delivery controls are disabled while capture/upload is pending.

Images are resized/re-encoded as JPEG, capped at 1.5 MB and have EXIF removed on the app. Up to three photos per order. Storage is the existing private staging document bucket under drivers/{driverId}/delivery-proof/{orderId}/; no public URLs or new S3/IAM configuration. Object encryption AES256 and SHA256 checksum; record contains key, uploader, upload timestamp, bytes and SHA256. Existing account-deletion upload fence/prefix rules are preserved. Failed DB attachment may leave an unreferenced private object; it is never shown as a saved proof or returned through the read API.

POST /driver/orders/{id}/delivery-proof accepts proofId/fileData and financial assignment offerId/attempt where applicable. Only assigned driver in arrived_at_customer/at_customer can append a new proof; conditional update fences driver, stage, attempt and three-photo limit. GET on the collection lists metadata, GET /{proofId} returns checked bytes only for the assigned driver, including after delivery. No arbitrary bucket/key input, no unauthenticated object access. No delivery/payment/hold/settlement changes. References remain in WizzOrders.deliveryProofs/deliveryProofIds. Admin-console photo viewer is not part of this change; metadata is stored with the order for authorized evidence retrieval.

Published only DriversApi-staging using selective ZIP patches and revision/hash guards, preserving all other bundle entries and financial functions. Synthetic smoke uncovered request-body parsing and it was corrected before final verification. Invocation immediately following the corrected deployment briefly used a prior execution environment; downloaded code/hash and subsequent full smoke confirmed the corrected runtime.

Validation: 9 proof-handler tests plus 16 existing route/issue tests (24 initially, then added HTTP body test = 25 backend checks); 9 frontend preprocessing/session/retry/receipt/delivery/completion tests passed. Targeted analyzer: no errors/warnings, style infos only. Native iOS profile build 247 succeeded.

Live verification used an isolated disposable order and generated JPEG, never the user's active order. Verified upload, identical replay, list, authenticated bytes/SHA, rejected unrelated driver, unchanged status/financial fields, reading after delivered, and complete deletion of the test order and versioned S3 objects.
